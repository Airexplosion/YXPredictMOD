# 规则与实现边界

## 当前规则（0.3.1，规则3）

积分版，不兑换认证时长。首次赠送1000分。八个玩家独立持仓，同一时刻每个玩家持有一个预测名次；允许多人押同一名次。不要求八人全买。

每轮修炼阶段可买入、增持、减半、清仓或换预测，第5轮不再永久封盘。每次买入1～10000整数积分，余额不得透支。前1～5轮买入对正中利润加成8/6/4/2/0%，之后为0。买入按当前赔率新增固定的正中返还权益，旧权益不重算；同名次权益合并。每人每局最多512次操作，累计投入上限512万分，正中权益上限2.56亿分。乘法有明确界限，不使用ILRuntime不支持的溢出检查指令。

减半出售 `floor(剩余正中权益 / 2)`，按出售比例释放剩余成本；清仓出售全部，成本归零。出售所得为 `floor(出售权益 × 10000 × 97 / (当前含加成万分倍率 × 100))`，报价为0时出售所得也为0。所有取整向下。参考市值和浮盈亏不是已入账余额。

换预测一次完成清仓与新买入，旧仓按当前报价折价3%出售，新仓按目标名次当前报价与输入积分建立；可用出售所得支付。先验证新名次、余额、额度和版本，失败时不出售旧仓。玩家清仓后可以重新买入。

正中返还剩余权益，差一名返还 `floor(剩余权益 / 4)`，其余为0，第1/8名不相邻。淘汰且取得确定名次后，该玩家停止交易并立即结算；完整最终结果到达后结算其余玩家。逐人Resolved标记和最终Settled标记防止重复派奖。面板历史记录累计投入、出售所得、结算返还与净收益。

单人面板和总表共用每个玩家的目标名次草稿。无持仓且未手动选择时为0，界面通过输入框占位符显示「？」；首按加号选1、减号选8，再循环1～8，也支持直接输入。实际持仓名次发生变化时覆盖草稿，普通报价刷新保留草稿；切换对局恢复该局真实持仓并清空未购买草稿。总表按有购买记录的剩余权益/旧票在前、其余在后稳定分组，只移动行的父节点，不重绑玩家下标；清仓恢复未持仓组。该状态不进入积分存档。

## 动态报价

游戏边界：`Proto.BattlePlayerData.rank` 与 `Proto.LifeRankInfo.rank` 使用0～7。真实客户端 `PlayerScoreItem.Refresh` 的IL在读取rank后加1再显示。桥接统一通过 `GameRanks.FromProtocol` 转换成1～8，越界值映射为未知0；通过 `GameRanks.ReadState` 仅给非正命元玩家填确定名次。整局结果也转换，确保原始0能正确表示冠军。0.2.8及以前直接使用原始值，会触发“确定名次与存活人数尚未对齐”并阻塞整批结算；修复不放宽核心的重复名次/存活人数校验，不修改已锁定权益，不凭命元排序生成结果。旧待结算记录重新收到同局正确状态即可恢复，无需迁移格式或重置余额。

开盘时按UID查询数据站 `data/elo/p/<uid最后两位>.json` 的rating和sigma，不用保守排序分cons替代Elo。AI、无公开UID、未收录或请求失败显式使用3000基准。Elo快照不随对局刷新；报价随回合和公开命元、胜负轮数、淘汰状态变化。sigma记录但不参与定价。

存活玩家的模型强度为 `Elo + clamp((命元 - 存活者平均命元) × 8, -800, 800) + clamp((胜轮数 - 负轮数) × 35, -350, 350)`。权重为 `exp(max(-12, (强度 - 最大强度) / 600))`。通过256个玩家子集动态规划得到Plackett–Luce边缘排名概率。淘汰玩家固定到已确认的末尾名次，仅在存活玩家之间分配剩余名次；未知、重复或与存活人数不符的淘汰信息暂停交易，不能凭命元排序猜最终名次。

加权概率 `q(i,r) = P(i,r) + 0.25 × P(i,r-1) + 0.25 × P(i,r+1)`，边界外为0。正中基础倍率 `clamp(0.90 / q, 1.01, 50)`，保留四位小数；两档都不可能的q为0时，出售价值为0。买入只开放精确名次仍可能达到的选项；已有持仓仍可按相邻奖励价值出售。早猜加成 `effective = min(50, 1 + (base - 1) × bonus)`，存为整数万分倍率。

模型不分析完整卡组、对位或未来抽牌，供观众根据游戏理解发现模型偏差。参数未进行回测，不是数据站提供的赔率，不代表官方概率。数据站分数来自共享的Weng-Lin/Plackett–Luce技术分，并非普通两人Elo。

## 交易窗口与状态顺序

只允许实时观战、裁判且当前账号不在参赛名单中；历史回放及参赛者淘汰后观战均不能交易。游戏桥读取修炼阶段、正计时、当前GameStatus整局ID和回合一致、SDK确认没有战斗执行器播放，全部满足才标记TradingOpen。点击操作前立即重新轮询。

同时监听BattleResult/AllBattleResults，并核对玩家UID、结果轮次；结果收到后将整局ClosedThroughRound单调推进。还读取管理器已有的结果，防止重载遗漏。已知结果轮次即使仍在修炼画面、旧状态返回或重载也不能再交易；下一回合取得完整局势后重新开放。交易不只依赖动画状态。状态回退会关闭窗口，不恢复早猜加成。

每次报价变化、交易及逐人结算推进TradeVersion。操作携带用户看到的版本，最新轮询后不一致就拒绝成交；同版本的重复操作也会被拒绝。修炼期命元等公开状态变化会更新报价。存档恢复后的窗口默认关闭，必须取得新状态后开放；缺失数据保留持仓，继续等待。

最终结果通过UID映射到开盘玩家顺序，八人名次须构成1～8完整排列。部分淘汰的名次须明确且不矛盾。收到整局结束信号后永久停止交易，不完整结果保持待结算，不能靠本地单场动画结束触发整局结算。

## 存档、升级和失败处理

通过一次 `ctx.Data.Set("predictionBook.v1", snapshot)` 保存余额、盘口、报价快照、操作版本、结果截止轮次、持仓、命元及换牌走势与结算记录。格式5为每个盘口记录规则号、调仓数据及按玩家顺序存放的平铺回合/命元、回合/剩余换牌列表；不存交易窗口开放状态。支持读取格式1/2/3/4，旧版模组会拒绝格式5。每个盘口沿用创建时的规则，旧盘口不自动转换成动态玩法。

规则1为旧版仅正中返还，规则2为固定票差一名返25%；两者都每人一张不可修改票、第5轮结束封盘，并保留原赔率及所有历史金额。新盘口使用规则3。旧盘口没有补发奖励或重新计价。

SDK写入抛错时恢复内存备份。坏存档不重置赠分，读取时校验动态报价、权益边界、确定名次、Resolved与已发总额。SDK通道没有落盘事务回执，不能声称具备断电时的数据库级持久性。

切换观战、退出、断线和热重载不自动退款；重返同局后可补齐结果。最多保留12局，优先清除最旧已结束盘口；都未结束时暂停开新盘。关闭“允许积分预测”仅禁止买入和换预测，允许减半/清仓及自动结算；停用整个模组不再处理状态。

账本仅用于本地娱乐，没有跨用户对账或可信服务器。认证时长接口留空；以后有正式接口，应由加载器账本验证身份、幂等扣款、报价截止与结算，不能直接把本地积分兑换成认证时长。

## 0.1.2 解释器兼容修复

0.1.1实机日志已显示八人Elo命中，卡点在后续开盘。使用[官方ILRuntime v2.1.0源码](https://github.com/Ourpalm/ILRuntime/tree/v2.1.0)构建独立解释器，将SDK Core和net40探针作为热更程序集载入，复现 `Odds.Probabilities` 二维数组访问的 `IndexOutOfRangeException`。把二维概率/赔率表换成 `playerIndex * 8 + rankIndex` 的一维数组，快照改为显式循环复制。磁盘存档原本就是64元素的平铺列表，因此无需迁移。

解释器随后发现原先的 `checked(stake * rate)` 生成了不支持的 `Mul_Ovf`。现先验证单注和倍率边界（最大乘积50亿，远小于Int64上限），使用普通乘法；结算加法先检查余额上限，不再生成溢出检查指令。保持原来的数值保护和向下取整规则。

修复后的解释器探针已通过：八名不同Elo玩家开盘、扣款下注、JSON存档恢复、第6轮封盘、最终名次结算及重复结果幂等。默认构建现在执行 `scripts/check-interpreter.ps1`，不再只依赖普通CLR测试和静态checker。该测试覆盖官方解释器语义，不能替代当前游戏客户端全部原生绑定与整局实测。

界面等待时先显示已知名单；开盘/更新错误明确显示并去重记录，避免进度停留在查询中的旧文案。表头采用独立列，修复长空格排版导致的错位。

按用户指定比例新增 25% 档位，正中和差一名共用冻结的票据赔率与早猜加成。`Ticket.ReturnFor` 统一用于实际结算、存档派奖校验及界面结果显示，防止三处规则不一致。面板显示当前盘口规则、两档返还预览与最终正中/差一名/未中结果；历史盘口按其原规则显示。

解释器探针覆盖同局正中与差一名两张票、JSON 恢复、第 6 轮封盘、最终派奖及幂等重放。新规则通过普通整数运算实现，继续避免不支持的溢出检查指令与多维数组。
