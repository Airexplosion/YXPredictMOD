# Independent free-points room server

Node 22+; no third-party dependencies. Start with `node server/server.mjs` from the repository root, or run `node --test server/rooms.test.mjs` for tests.

Environment: `ROOM_HOST` defaults to `127.0.0.1`, `ROOM_PORT` to `8123`, `ROOM_DATA` to `./room-data`. External clients require HTTPS; proxy `/prediction/` to `http://127.0.0.1:8123/` with the prefix removed. Preserve Authorization; set X-Real-IP from the actual remote client. Only a loopback proxy's X-Real-IP is trusted. Do not expose the internal HTTP port publicly.

Production runs independently on the existing auth host, at `https://auth.kaigua.vip/prediction`, Windows task `yx-prediction`, source `C:/yx-prediction/app`, data `C:/yx-prediction/data`, wrapper `C:/yx-prediction/run.ps1`. The task starts on boot and restarts after failure. It uses no auth database, keys, environment file or license API. Nginx changes are limited to the new prefix; the prior vhost is backed up at `C:/yx-prediction/auth-vhost-before.conf`.

`GET /healthz` reports health. `POST /v1/room` accepts register/create/join/lookup/random/view/sync/trade. Register returns a random bearer credential. Other operations require that credential; public views do not include other credentials. Game ID and roster must match. Only the host may synchronize results. Trading requires a current version and unique operation ID; repeated operation IDs return the latest state without charging again, even after settlement. Successful mutations are saved before responding; save errors roll back memory.

Each account starts with 1000 free points. Pools are independent for each game player, split among exact-rank winners in proportion to their remaining contributions. No winner means a refund for that pool. Closing a position refunds 97% of its original contribution, not a speculative market price. Shares do not promise fixed odds; the final pool determines returns. No purchase, withdrawal, transfer or license-time conversion exists.

The host is trusted to provide game results. This version does not prove official account ownership or independently verify game servers. Creating new local identities is possible; points have no redeemable value. Room codes are invitations, not passwords. There are limits of 32 members/room, 1000 rooms, 10000 identities, 20000 actions/room, 32KB requests and 600 requests/IP/minute. Completed rooms are retained for history; capacity cleanup and identity recovery are manual operational work for this initial version.

Persistence: JSON snapshot with fsync and atomic rename, one writer per directory using a PID lock. Restart retains balances and holds but resets host heartbeat freshness. Crash-stale locks are reclaimed only when their PID no longer exists. An invalid lock fails closed. Back up `rooms.json` from the atomically replaced file, and retain its access restrictions; it contains bearer credentials. Do not commit data, logs or credentials. For upgrades, stop the task and verify its Node process has exited before replacing sources or copying data; restart and verify both room and existing auth health endpoints. No authentication service restart is needed.

Tests include real HTTP clients and disk restart. Public deployment smoke tests used two synthetic identities and a completed synthetic game, without real game or license data. Lobby launcher, room panel, empty matching result and native spectate confirmation/cancel passed in-game; no live funded room was available to test the complete cross-game transition and automatic join.

Random selection only returns a room code, game ID, native game room ID, member count and round. It does not add membership or spend points. Candidates must have an active host heartbeat, open trading, a nonempty stake pool, a native room ID, spare capacity and unfinished status. The client must enter the matching game through the native lobby panel before sending the normal join request. Native game room IDs are optional for old clients, validated and immutable once supplied, and never replace game IDs as accounting identities.

Version 0.5.2 adds authenticated `lookup` for a user-entered invitation code. It returns the same minimal selection metadata without joining or spending; unfunded or temporarily paused rooms are allowed, but the host must be online, a native room ID must be present, and the room must not be full or ended. The client enters native spectating and verifies the game before the ordinary join action.

Version 0.6.0 authenticated requests may include identity {name, uid}; values are self-reported display identity, not verified official account ownership. Updated identities are persisted only when changed. Room memberDetails returns a non-bearer public member identifier, display name and supplied game UID to existing members; discovery/lookup metadata never includes the member list or credentials. Repeating join does not add a new member. Client notifications compare stable public IDs to avoid duplicate arrival prompts on polling, and initialize silently on a new/reconnected session. No raw bearer keys appear in public room responses.

0.6.2: authenticated findGame(nativeId) returns whether the selected native game has a pending prediction room, and whether its host is fresh and capacity allows joining. It does not join or expose credentials. Creation is unique for each unfinished game/native room; simultaneous duplicate create requests reuse the existing room via ordinary join instead of opening another pool. Offline hosts remain discoverable as unavailable, preventing duplicate pools while existing stakes remain unresolved. Old duplicate rooms are not deleted or merged.

## 0.7.0 rule version 2

New rooms created with a 64-entry `baseRates` snapshot use rules=2. A room without these fields keeps legacy pool rules=1, including rooms persisted by older versions. Upgrading a host never changes a pending room's rules. All host/guest clients should use 0.7.0 for rule-2 rooms; older guests do not understand the rate matrix.

The host sends the existing single-player base quote in snapshot player order. The server reorders by UID. Public-state base quotes may refresh within a round; wager coefficients freeze for the round and only recalculate on a later round. `quote = base * factor`, with factor=clamp(1 + 0.25*(1-8*selectedContribution/totalContribution), 0.75, 1.25); no wagers means factor 1. Outstanding unresolved position costs across members supply the weights. Unreachable base quotes remain zero; other quotes clamp 1.01..50 like single player. Equal quotes produce equal locked rights, half/full sale returns and payouts to the single-player ledger; server/rules.test.mjs replays generated C# ledger fixtures to verify this.

Rule-2 purchase locks floor(stake*rate/10000) claim. Exact final rank returns claim; adjacent returns floor(claim/4); other ranks return zero. Sell half removes floor(claim/2); sale refund=floor(removedClaim*10000*97/(currentRate*100)), zero rate returns zero. Cost is proportionally released with integer flooring; switch is atomic, failed validation restores all state. Eliminated positions resolve once, complete results finish the room without repaying them. Counts remain after full liquidation, limit512/account/player. Max balance1e12. New rule room action cap131072 covers32*8*512; legacy cap20000 preserved.

The earlier README's pool distribution and 97%-of-principal paragraph applies only to rule1; it is not the rule2 model. Discovery, auth and host trust boundary are unchanged. No money or redeemable currency exists. Snapshot base quotes are host-reported, not independently verified against the official game.

Build and test both `node --test server/rooms.test.mjs server/rules.test.mjs`. A C# oracle can be regenerated with `dotnet run --project tests/PredictionChecks.csproj -- --rule-parity .cache/single-player-parity.json`; build.ps1 compares its hash to the reviewed checked-in fixture and stops on drift. Fixture game identities and states are synthetic.
